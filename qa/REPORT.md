# Отчёт QA

Проверены вместе PR #1 (`feat/frontend`, f8412f9) и PR #2 (`feat/backend-api`, 61f2bc8), слитые локально в одну ветку. Дата: 2026-10-24. Первый прогон был на версиях до ревью, цифры ниже с повторного прогона на версиях после ревью.

## Как повторить

```bash
docker compose up --build              # db + backend :3000 + frontend :8080
cd backend && npm ci && npm run seed:large   # 10 000 учеников, ~300 000 оплат
cd ../qa && npm ci
node bench.mjs                         # нагрузка: каждый эндпоинт 20 с, 10 соединений
node sql-count.mjs                     # SQL на HTTP-запрос (db запущена с log_statement=all, см. ниже)
cd ../e2e && npm ci && npm run test:e2e  # браузерные тесты, mobile 390×844 и desktop 1280×800
```

Для подсчёта SQL базу нужно запустить с логированием всех запросов:

```yaml
# docker-compose.override.yml
services:
  db:
    command: ["postgres", "-c", "log_statement=all"]
```

## SQL-запросов на HTTP-запрос

Подсчёт по логу Postgres (`log_statement=all`). Не считаются BEGIN/COMMIT и `SELECT 1` от healthcheck контейнера backend.

| Запрос | HTTP | SQL | норма | итог |
|---|---|---|---|---|
| GET /debtors | 200 | 1 (`COUNT(*) OVER()`) | ≤ 2 | OK |
| GET /students | 200 | 2 (данные + count) | ≤ 2 | OK |
| GET /students?search= | 200 | 2 | ≤ 2 | OK |
| GET /students/:id | 200 | 1 | ≤ 2 | OK |
| GET /students/:id/payments | 200 | 2 | ≤ 2 | OK |
| POST /payments | 201 | 1 (несуществующий ученик ловится по FK → 404) | ≤ 2 | OK |
| POST /students | 201 | 1 | ≤ 2 | OK |
| PATCH /students/:id | 200 | 1 | ≤ 2 | OK |
| DELETE /students/:id | 204 | 1 | ≤ 2 | OK |

N+1 нет: число запросов не зависит от размера страницы.

## EXPLAIN ANALYZE

- `/debtors` (октябрь 2026, 2 769 должников): `Bitmap Index Scan on payments_paid_at_idx` → HashAggregate → Hash Left Join со `students`, top-N heapsort. Execution Time 17 мс. Seq Scan по `payments` нет; Seq Scan по `students` (10 000 строк, 134 страницы) ожидаем, так как нужны все ученики.
- Поиск `ILIKE '%ала%'`: Seq Scan по `students`, 7 мс. Планировщик не берёт trigram-индекс на 10 000 строк, потому что полный проход дешевле; на 2 буквах trigram неприменим в принципе. Для текущего объёма это нормально.
- Оплаты ученика: `Index Scan Backward using payments_student_id_paid_at_idx`, 0.06 мс.

## Браузер (Playwright)

`e2e/`, 19 тестов, проходят на mobile (390×844, touch) и desktop (1280×800):

- Должники: открывается текущий месяц; общий долг, число должников и суммы карточек совпадают с API; «Показать ещё» запрашивает `offset=50`; смена месяца; возврат на уже открытый месяц без нового запроса; следующий месяц после текущего недоступен.
- Оплата из карточки должника: сумма подставляется равной долгу; после частичной оплаты долг уменьшился; после полной ученик исчез из списка.

- Ученики: создание, ошибки валидации видны в форме (4 поля подсвечены, текст ошибки телефона), поиск, карточка, изменение, удаление → 404.
- Переключение вкладок «Должники» ↔ «Ученики» трижды: 0 запросов к API.
- Карточка ученика: запрос оплат стартует до ответа по ученику (нет водопада).
- Нет ошибок в консоли; нет горизонтального скролла на 360 px (списки и форма оплаты).

## Найденные баги и замечания

### 1. PR #1: `docker compose up` падает на ветке `feat/frontend` (важно)
`frontend` зависит от сервиса `backend`, которого в этой ветке нет:
```
service "frontend" depends on undefined service "backend": invalid compose project
```
Кроме того, PR #1 и PR #2 конфликтуют в `docker-compose.yml`. Предложение: влить PR #2 первым, затем PR #1 переносит на новый `main` и оставляет оба сервиса. После ручного разрешения конфликта (оба сервиса) стек поднимается и всё работает.

### 2. PR #2: поиск не экранировал `%` и `_` (исправлено)
`GET /students?search=%` и `?search=_` возвращали всех учеников: Prisma `contains` передаёт строку в `ILIKE` без экранирования. Исправлено в 61f2bc8, перепроверено: теперь 0 результатов.

### 3. PR #2: можно создать двух учеников с одним телефоном (вопрос)
`POST /students` с уже существующим телефоном отвечает 201. По контракту это не запрещено, но в задачах QA упоминается 409. Нужно решить: телефон уникален (тогда unique-индекс и 409) или нет (тогда так и оставить).

### Не баг, особенность песочницы
В этой облачной среде `npm ci` внутри `docker build` не достаёт до registry без прокси и его сертификата. Для проверки образы собирались с временно подставленным сертификатом; Dockerfile проекта при этом не менялся, и у обычного пользователя сборка идёт без этого.

## Что сгенерировал ИИ и где он ошибся

ИИ (Claude) написал `bench.mjs`, `sql-count.mjs`, тесты в `e2e/` и этот отчёт.

- Первый прогон `bench.mjs` показал «ПРЕВЫШЕНИЕ» везде при p95 ≈ 4 мс. Ошибка: autocannon подменяет путь из `url` путём из `requests`, и префикс `/api` терялся, так что все запросы шли в 404. Заметил по столбцу «ошибки» (≈ 80 000 на эндпоинт) и неправдоподобно малому времени. Исправлено: базовый адрес отдельно, путь с префиксом.
- В тесте учеников ожидание тоста упало в strict mode: два тоста («добавлен» и «сохранены») видны одновременно. Исправлено фильтром по тексту.
- Полностраничные скриншоты при `deviceScaleFactor: 3` весили 29 МБ. Переделано на скриншот экрана с плотностью 2 (2 МБ).
- Счётчик SQL иногда показывал на `/debtors` 2–3 запроса вместо 1. Причина: в окно замера попадал `SELECT 1` от healthcheck backend, который идёт каждые 10 с. Нашёл, выведя сами строки лога при расхождении; healthcheck исключён из подсчёта.
- Упавшие тесты оставляли в базе учеников группы E2E. Добавлен `global-teardown.ts`, который удаляет их после любого прогона.
